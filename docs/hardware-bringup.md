# Hardware bring-up — Minew MHS starter kit วันแรกบนโต๊ะ

คู่มือนี้เรียงลำดับให้ **ไม่มีอะไรวิ่งไปปลุกใครได้** ระหว่างทดสอบ ทำจากบนลงล่าง อย่าข้ามข้อ

อุปกรณ์ในชุด: MG3 ×2, S1 (อุณหภูมิ/ความชื้น — **ตัวเดียวที่ยืนยันกับเครื่องจริงแล้ว**), C10 (บัตร), B7 (สายรัดข้อมือมีปุ่ม), B10 (ปุ่มฉุกเฉิน), E8S (แท็กทรัพย์สิน/accelerometer), MBT01 (แท็กกันถอด)
ตัวถอดรหัสของ C10/B7/B10/E8S/MBT01 เขียนจากเอกสารสาธารณะกับ simulator เท่านั้น ยังไม่เคยเห็นแพ็กเก็ตจริง ดู [`docs/platform/minew-kit.md`](platform/minew-kit.md) และ [`docs/minew-mhs.md`](minew-mhs.md)

## 0. ก่อนเสียบไฟ: ปิดทางที่จะแจ้งเตือนคนจริง

1. `ALERTS_SHADOW=true` ต้องเปิดอยู่ (ค่าเริ่มต้นของ `infra/prod/compose.yaml` และ `infra/prod/setup.py --shadow`) backend จะ log ว่า
   `ALERTS_SHADOW is on: events are recorded, no alerts, notifications or automations run`
   ให้ยืนยันด้วยตาว่าเห็นบรรทัดนี้ใน log ตอน start ก่อนเริ่มทดสอบ
2. **อย่าสร้าง notification channel ใด ๆ** (LINE / webhook / email) ระหว่าง bring-up ถ้ามีอยู่แล้วให้ปิดก่อน
3. อย่าสร้าง automation หรือ alert rule ที่ผูกกับ tamper / button ในขั้นนี้ เหตุการณ์จะถูกบันทึกลง event log อยู่แล้ว ดูจาก log พอ
4. ทำบน LAN ที่ควบคุมเอง ไม่เปิด port forward

> เหตุผล: เฟรม tamper (A1‑20) และการอนุมานว่า "กดปุ่ม" ของ B10 ยังไม่ผ่านการยืนยันกับเครื่องจริง ถ้าเปิดช่องแจ้งเตือนไว้ การทดสอบจะสร้าง false alarm และทำให้คนเลิกเชื่อระบบ (alarm fatigue) ซึ่งแก้ยากกว่าบั๊ก

## 1. ตั้ง MG3 (ทำทีละตัว)

ตั้งผ่าน Gateway Configurer บน iOS ตามที่บันทึกไว้ใน [`docs/mqtt.md`](mqtt.md)

| หัวข้อ | ค่าที่ต้องใช้ | ตรวจอย่างไร |
|---|---|---|
| Data format | **JSON‑LONG** | แถวที่ส่งขึ้นมาต้องมี `mac`, `rawData`, `rssi`, `timestamp` ครบ ถ้าได้แต่ `mac`+`rssi` แปลว่ายังเป็น JSON‑SHORT — Aether ถอดรหัสไม่ได้เลย |
| Transport | MQTT over TLS, **port 8883** | ใน iOS เลือกสกีม `mqtts://` |
| CA | อัปโหลดไฟล์ CA ของ broker (`.secrets/mqtt/broker/ca.crt`) | ห้ามปิด server certificate verification |
| Credential | username/password **ต่อ gateway** ที่ออกจากหน้าเว็บ Aether (`POST /api/v1/gateways` แสดง token ครั้งเดียว) | gateway ตัวที่สองต้องใช้ credential ของตัวเอง ห้ามใช้ซ้ำ |
| Upload interval | **5 วินาที** | ถี่พอให้เห็น event แต่ยังไม่ท่วม retention 100 packet/gateway |
| NTP | เปิด และตั้ง time zone ให้ตรง | `timestamp` ในแถวมาจาก gateway ถ้าเวลาเพี้ยน การไล่ event ย้อนหลังจะอ่านไม่รู้เรื่อง (ฝั่ง server ใช้ `received_at` เป็นหลักอยู่แล้ว) |
| Scan filter | **ปิดก่อน** ในช่วงแรก | จะได้เห็นทุกอย่างที่ gateway ได้ยิน รวมถึงแท็กที่ Aether ยังไม่รู้จัก |

### ตรวจว่า gateway ตรวจใบรับรองจริง (ทำครั้งเดียว ต่อ gateway)

ต้องพิสูจน์ว่า MG3 **ปฏิเสธ** CA ที่ผิด ไม่ใช่แค่ยอมรับ CA ที่ถูก:

1. อัปโหลด CA ที่ไม่เกี่ยวข้อง (เช่น CA ของ test อีกชุด) เข้า gateway แล้วสั่ง reconnect
2. ผลที่ถูกต้อง: **เชื่อมต่อไม่สำเร็จ** และไม่มี packet ใหม่เข้ามา (ตรวจด้วย `python3 infra/capture-golden.py list` — จำนวนแถวต้องหยุดนิ่ง)
3. ถ้ายังส่งได้ทั้งที่ CA ผิด แปลว่า firmware ไม่ได้ตรวจใบรับรอง → **หยุด** อย่าใช้เส้นทางนี้กับข้อมูลจริง บันทึกไว้ในตารางยอมรับด้านล่าง
4. อัปโหลด CA ที่ถูกกลับเข้าไป แล้วยืนยันว่ามี packet ใหม่อีกครั้ง

### เปิด scan filter หลังรู้จัก MAC แล้ว

หลังจากเก็บ golden ของทุกตัวเสร็จ ให้เปิด filter เพราะห้องที่มีคนเดินผ่านพร้อมโทรศัพท์จะกิน discovery budget ของ Aether จนแท็กจริงถูกเบียดออก (`DiscoveryLimit` ต่อ gateway)

- ทางเลือกที่ 1: filter ตาม **MAC prefix ของ Minew** ที่อ่านได้จากแท็กจริงในชุด (อย่าเดา prefix — อ่านจาก `capture-golden.py list` ก่อน)
- ทางเลือกที่ 2 (แคบกว่า ปลอดภัยกว่าในวอร์ด): filter ตาม **MAC เฉพาะตัว** ของแท็กที่ลงทะเบียนแล้ว

## 2. วนทีละอุปกรณ์

ทำทีละตัว เปิดแค่ตัวที่กำลังทดสอบ (ตัวอื่นเอาไปไว้ห่าง ๆ หรือถอดแบตเตอรี่) จะได้ไม่สับสนว่า MAC ไหนเป็นของใคร

ขั้นตอนร่วมของทุกตัว:

```sh
python3 infra/capture-golden.py list          # หา gateway id และ MAC ของแท็ก
python3 infra/capture-golden.py capture --gateway <GATEWAY_ID> --mac <AA:BB:CC:DD:EE:FF> --scenario <device> --note "fw ของ gateway/tag"
cd backend && go test ./internal/adapters/minew/ -run TestRealCaptures -v
```

`capture` จะแทนที่ MAC ด้วยนามแฝงให้อัตโนมัติ (ทั้งในช่อง `mac` และในไบต์ของเฟรม) ไฟล์จึงยังถอดรหัสได้และไม่พก identifier ของคนจริงเข้า repo ถ้าต้องการเก็บ MAC จริงจริง ๆ ใช้ `--no-anonymize` และรับผิดชอบเอง

หน้าที่ต้องเปิดดูควบคู่: **"เชื่อมต่ออุปกรณ์"** (topology) และ event log

### S1 — อุณหภูมิ/ความชื้น (เฟรม A1‑01 ยืนยันแล้ว)

- ทำ: วางนิ่งข้าง gateway `--scenario s1`
- ควรเห็น: node ชื่อ "Minew temperature & humidity" (หรือ "Minew S1" หลังได้เฟรม info) ค่าอุณหภูมิ/ความชื้นขยับช้า ๆ `frames` = `minew-ffe1-a101@1`
- ยังไม่ยืนยัน: เฟรม **A1‑08 (info/name)** — ตำแหน่ง MAC อยู่ที่ไบต์ที่ 4–9 ของ payload และชื่อรุ่นต่อจากนั้น ถ้าชื่อที่ขึ้นไม่ใช่ `S1` ให้เก็บไฟล์ไว้ อย่าแก้ decoder ตามใจ

### C10 — บัตร

- ทำ: `--scenario c10` (นิ่ง → กดปุ่มค้าง 3 วินาที → ปล่อย)
- ควรเห็น: iBeacon (UUID/major/minor) + `minew-ffe1-a103@1` (accelerometer) ค่า `accel_z` ประมาณ 1 g เมื่อวางราบ
- ยังไม่ยืนยัน: **รูปแบบเฟรมตอนกดปุ่มของ C10 ไม่มีเอกสาร** ถ้ากดแล้วไม่มีอะไรเปลี่ยนเลย ถือว่าปกติสำหรับตอนนี้ — เก็บไฟล์ `c10-press` ไว้เทียบกับ `c10-idle` แบบ byte-diff

### B7 — สายรัดข้อมือมีปุ่ม

- ทำ: `--scenario b7`
- ควรเห็น: iBeacon + accelerometer เหมือน C10
- ยังไม่ยืนยัน: รูปแบบ event ปุ่มกดของ B7 (catalog เขียนไว้ว่า "ยังไม่มีเอกสารยืนยัน")

### B10 — ปุ่มฉุกเฉิน

- ทำ: `--scenario b10` (ปล่อยนิ่ง 20 วินาที → กดปุ่มค้าง 3 วินาที → ปล่อย)
- ควรเห็น: Eddystone‑UID (`namespace` + `instance`) และ TLM (แรงดันแบตเตอรี่) ตอนกดปุ่ม **instance ควรเปลี่ยน** และ event log ควรมี `device.button` พร้อมหมายเหตุ `Eddystone-UID instance changed; press semantics unverified on hardware`
- ยังไม่ยืนยัน: **การอนุมานว่า instance เปลี่ยน = กดปุ่ม** มาจากคู่มือตั้งค่าสาธารณะ ไม่ใช่จากเครื่องจริง ถ้า instance ไม่เปลี่ยนตอนกด อย่าไปแก้ให้มันเปลี่ยน — บันทึกว่าเป็นคนละกลไก
- เตือน: `device.button` เป็น event ที่คนจะเอาไปผูกการแจ้งเหตุฉุกเฉิน ห้ามเปิด channel จนกว่าข้อนี้จะผ่านและมี golden test

### E8S — แท็กทรัพย์สิน

- ทำ: `--scenario e8s` (นิ่ง 30 วินาที → เขย่าเบา ๆ 30 วินาที)
- ควรเห็น: `minew-ffe1-a103@1` (accelerometer) และถ้ามี `minew-ffe1-a118@1` (vibration) ค่า `vibration` ควรเป็น 1 ช่วงเขย่า และกลับเป็น 0 เมื่อหยุด event log ควรมี `device.motion` / `device.motion_stopped` อย่างละครั้ง ไม่ใช่รัว ๆ
- ยังไม่ยืนยัน: **บิต vibration = บิตที่ 0 ของไบต์ที่ 8 ของ payload A1‑18** (`a1 18 <battery> <ts×4> <flag> <mac×6>`) และ `ts` 4 ไบต์เป็น big-endian ทั้งคู่มาจากตารางเอกสารสาธารณะ ต้องยืนยันด้วยการเขย่าจริงแล้วดูว่าไบต์ไหนเปลี่ยน

### MBT01 — แท็กกันถอด

- ทำ: `--scenario mbt01` (ติดสนิท → ดึงออก → ติดกลับ)
- ควรเห็น: iBeacon + `minew-ffe1-a120@1` ค่า `tamper` เปลี่ยน 0 → 1 → 0 และ event log มี `device.tamper` / `device.tamper_cleared` อย่างละครั้ง
- ยังไม่ยืนยัน: **บิต tamper = บิตที่ 0 ของไบต์ที่ 4 ของ payload A1‑20** (`a1 20 <battery> <flag> <mac×6>` คือไบต์ถัดจากไบต์แบตเตอรี่) decoder จงใจอ่าน **บิตเดียว** เท่านั้น ไม่นับค่าอื่นว่า "ถูกงัด" และถ้าไบต์แบตเตอรี่อยู่นอก 0–100 จะทิ้งทั้งเฟรม เพราะแปลว่าเรากำลังอ่าน layout ผิดรุ่น **ต้องยืนยันด้วยการงัดแท็กจริงแล้วดูว่าบิตนี้คือบิตที่เปลี่ยน** ถ้าเป็นบิตอื่น ให้แก้ `frames.go` พร้อมแนบ golden ทั้งสถานะติด/ถอด

### ชุด MOS smart office (MG4 + MSP01 + S4)

รายละเอียดทั้งชุดอยู่ที่ [`docs/platform/mos-kit.md`](platform/mos-kit.md) ตั้ง MG4 เหมือน MG3 ในข้อ 1 (JSON‑Long เป็นรูปแบบเดียวที่ MG4 มี) ต่างกันแค่ NTP ไม่จำเป็น เพราะ Aether ใช้เวลาฝั่ง server เสมอ และ `timestamp` ของ MG4 ที่เป็นสตริง ISO‑8601 ถูกข้ามไปโดยไม่ทำให้แพ็กเก็ตหาย

### MSP01 — PIR ตรวจคนในห้อง

- ทำ: `--scenario msp01` (ห้องว่าง 60 วินาที → เดินผ่านไป-กลับ 30 วินาที → ห้องว่างอีก 60 วินาที)
- ควรเห็น: `minew-ffe1-a111@1` ค่า `motion` เป็น 1 ช่วงเดินผ่าน event log มี `occupied` ครั้งเดียว และ `vacant` ครั้งเดียวหลังไม่มี motion ครบ 5 นาที (worker เป็นคนตัดสิน ไม่ใช่ uplink)
- ยังไม่ยืนยัน: **ตัวจริง `c30000161ebb` รายงาน `motion=0` ทั้ง 257 ตัวอย่าง** เมื่อ 2026-09-21 จึงยังไม่รู้ว่าบิต 0 ของ A1‑11 คือ PIR จริงหรือไม่ ต้องทดสอบโดยเดินผ่านหน้าเซนเซอร์เท่านั้น ถ้าเดินผ่านแล้ว `motion` ยังเป็น 0 ให้เก็บไฟล์ `msp01-walk` ไว้ แล้วใช้ "สอนสัญญาณ" แบบ `motion` แทนการแก้ decoder ตามเดา

### S4 — เซนเซอร์ประตู (ไม่มี decoder โดยเจตนา)

datasheet ของ S4 บอกเพียงว่ามีเฟรม "INFO / Combination Frame" และ SDK ของ Minew เรียงชื่อฟิลด์ของ combination frame ว่า `doorSensorAlarmStatus`, `tamperProofAlarmStatus`, `triggerAlarmStatus`, `openCount`, `closeCount`, `tamperProofCount` แต่ **layout ไบต์, service UUID และ frame/version byte ไม่มีเอกสารสาธารณะ** Aether จึงไม่ถอดรหัสเอง เพราะ decoder ที่เดาผิดจะสร้าง false door/tamper alarm

1. เก็บของจริงก่อน: `python3 infra/capture-golden.py capture --gateway <GATEWAY_ID> --mac <MAC ของ S4> --scenario s4 --note "fw ..."`
   (ปิด → เปิด → ปิด → เปิดฝากันงัด) ระหว่างนี้หน้า "เชื่อมต่ออุปกรณ์" จะเห็น S4 เป็น node ที่มีฟิลด์ `unknown` เช่น `ffe1:a1:0x??:len=..` หรือ `ad:0x16:...` นั่นคือเฟรมที่ยังไม่มีกฎ
2. สอนสัญญาณ `door` (ข้อ 2.6): **ขั้นที่ 1 ปิดประตูไว้นิ่ง ๆ**, **ขั้นที่ 2 เปิดประตูค้างไว้** (หรือเปิด-ปิดช้า ๆ แต่ให้ช่วงเปิดยาวกว่ารอบอัปโหลด) เลือก candidate ที่เป็น "ไบต์ … เปลี่ยนจาก 0x00 เป็น 0x01" ไม่ใช่ไบต์ที่ค่าเพิ่มทีละ 1 (นั่นคือตัวนับจำนวนครั้งที่เปิด จะค้างเป็นค่าใหม่แม้ปิดประตูแล้ว)
3. หลังยืนยัน: สัญญาณที่ตรง = `door=1` (เปิด), ไม่ตรง = `door=0` (ปิด) บันทึกลง reading ทุก uplink ที่มีเฟรมนั้น และ event log ได้ `door_open` / `door_closed` แบบ edge-triggered อย่างละครั้ง uplink ที่ไม่มีเฟรมนั้นเลย (เช่นมีแต่ info) จะไม่เปลี่ยนสถานะ
4. กด **ทดสอบกับข้อมูลย้อนหลัง** เปิด-ปิดประตูหลายรอบก่อน แล้วดูว่าจำนวนครั้งที่ตรงสอดคล้องกับที่เปิดจริง
5. เมื่อมีไฟล์ golden ของสถานะปิด/เปิด/กันงัดครบ และรู้แน่ว่าไบต์ไหนคืออะไร จึงค่อยเขียน decoder ใน `frames.go` พร้อม golden test แล้วค่อยพิจารณา `Verified: true` ตามข้อ 5 — จนกว่าจะถึงตอนนั้น profile `minew-s4-pending@1` คงเป็น `Verified: false`

1. **B10 ไม่เปิด slot Eddystone-UID** ขณะที่ตัวอื่นเปิด การเดาว่า "กดปุ่ม = instance เปลี่ยน" ตามคู่มือสาธารณะจึงใช้กับเครื่องจริงไม่ได้เลย ถ้าต้องการลองตามคู่มือ ให้เปิด slot UID ในแอป Minew ก่อน
2. **ไม่มีอุปกรณ์ตัวใดที่ค่า instance เคยเปลี่ยน** ตลอดการเก็บข้อมูล ดังนั้นไม่มี false positive แต่ก็ไม่มีการกดปุ่มที่ตรวจจับได้เลย
3. ไม่มีเฟรม `unknown` ปรากฏเลย แปลว่า decoder เข้าใจทุกอย่างที่ gateway ส่งมา ถ้ากดปุ่มแล้วไม่มีอะไรใหม่โผล่ แปลว่าเฟรมนั้นไม่ได้มาถึง gateway ไม่ใช่ว่าระบบอ่านไม่ออก

## 2.6 สอนสัญญาณแทนการเดา (วิธีที่แนะนำ)

อย่าเดา byte อีก ใช้ "สอนสัญญาณ" ในหน้า เชื่อมต่ออุปกรณ์ แทน

1. เปิดอุปกรณ์ในแถบขวา เลื่อนลงไปที่ **สัญญาณที่สอนไว้** แล้วกด **เริ่มสอนสัญญาณ**
2. เลือกว่าจะสอนอะไร ปุ่มกด กันถอด น้ำรั่ว การเคลื่อนไหว หรือ **ประตู** (`door`: ขั้นที่ 1 ปิดไว้, ขั้นที่ 2 เปิดค้าง — ตรง = เปิด, ไม่ตรง = ปิด ดูหัวข้อ S4 ด้านบน)
3. **ขั้นที่ 1 ปล่อยนิ่ง** วางอุปกรณ์ไว้เฉย ๆ จนครบเวลา หน้าจอนับจำนวนสัญญาณที่ได้ยินให้เห็นสด ๆ
4. **ขั้นที่ 2 กระตุ้น** กดปุ่มย้ำ ๆ หรือถอดป้ายซ้ำ ๆ จนครบเวลา
5. ระบบเทียบสองช่วง แล้วเสนอสิ่งที่โผล่เฉพาะตอนกระตุ้น พร้อมคำอธิบายภาษาไทยและจำนวนครั้งที่เห็น เลือกอันที่ตรงกับที่ทำจริง กด **ยืนยันและใช้งาน**
6. ติ๊ก **ใช้กับทุกตัวที่เป็นรุ่นนี้** ถ้าต้องการให้สอนตัวเดียวแล้วใช้ได้กับทุกตัวที่ลงทะเบียนเป็นรุ่นเดียวกัน
7. กด **ทดสอบกับข้อมูลย้อนหลัง** ก่อนไว้ใจ เพื่อดูว่าถ้าใช้กติกานี้กับ 10 นาทีที่ผ่านมาจะเด้งกี่ครั้ง ถ้าเด้งรัว แปลว่าเลือกผิดอัน

ถ้าระบบบอกว่าไม่พบอะไรต่างจากตอนปล่อยนิ่ง ให้เช็กสามอย่างตามลำดับ: แท็กอาจต้องตั้งค่าในแอป Minew ให้กระจายสัญญาณตอนกด, scan filter ของ MG3 อาจกรองทิ้ง, หรือช่วงกดสั้นกว่ารอบอัปโหลดของ gateway

เมื่อสอนสำเร็จ การกดจะกลายเป็นเหตุการณ์ `button` จริง และกฎ **ปุ่มฉุกเฉิน SOS** ที่ติดมากับ workspace จะเปิดการแจ้งเตือนระดับวิกฤตให้ทันที

## 3. เมื่อแท็กขึ้น `Unknown`

Aether รายงานสิ่งที่ได้ยินแต่ยังไม่เข้าใจเป็นรายการสั้น ๆ ในฟิลด์ `unknown` ของ reading (เห็นได้จาก `GET /api/v1/live` และหน้า "เชื่อมต่ออุปกรณ์") เช่น

```
ffe1:a1:0x22:len=14          เฟรม Minew เวอร์ชันที่ยังไม่มีกฎถอดรหัส
ad:0x16:uuid=feaa:type=0x30  Eddystone ชนิดที่ยังไม่รองรับ
ffe1:a1:0x01:mac-mismatch    MAC ในเฟรมไม่ตรงกับที่ gateway รายงาน
ffe1:a1:0x03:accel_x=oor     ค่าหลุดกรอบ ถูกทิ้งเฉพาะฟิลด์นั้น
```

**สิ่งที่ต้องทำ:** เก็บไฟล์ด้วย `capture-golden.py capture ... --label <device>-unknown` แนบไฟล์นั้นไปกับ issue แล้วหยุด
**สิ่งที่ห้ามทำ:** เดาความหมายของไบต์แล้วเขียน decoder ตามที่เดา — ระบบนี้แยก "ถอดรหัสจากเอกสาร" กับ "ยืนยันกับเครื่องจริง" ออกจากกันเพื่อไม่ให้ค่าที่เดาไหลเข้า alert

## 5. เปลี่ยน `Verified: true` เมื่อไหร่

`Verified` ใน [`backend/internal/domain/catalog.go`](../backend/internal/domain/catalog.go) แปลว่า **มี golden test จากอุปกรณ์จริงในรีโพนี้ที่ผ่าน** ไม่ใช่ "อ่านเอกสารแล้วมั่นใจ"

ลำดับที่ถูกต้อง:

1. เก็บไฟล์ด้วย `capture-golden.py` จากอุปกรณ์จริง
2. รัน `go test ./internal/adapters/minew/ -run TestRealCaptures -v` แล้ว **อ่านบล็อก `expect` ที่เทสต์แนะนำด้วยตา** เทียบกับค่าที่อุปกรณ์/แอปแสดงจริง
3. ถ้าตรง ใส่บล็อก `expect` ลงในไฟล์ golden แล้วรันเทสต์อีกครั้งให้เขียว
4. ค่อยเปลี่ยน `Verified: false` → `true` ของ profile นั้นใน `catalog.go` (ไฟล์นี้เป็นของทีมอื่น — แก้ใน PR แยก พร้อมอ้างไฟล์ golden)
5. ถ้าอุปกรณ์หนึ่งมีหลายเฟรมและยืนยันได้แค่บางเฟรม ให้คง `Verified: false` แล้วเขียนไว้ใน `Notes` ว่าเฟรมไหนผ่านแล้ว

## 6. ทดสอบ roaming / RSSI ระหว่าง MG3 สองตัว

วาง MG3 สองตัวห่างกันพอจะเดินระหว่างกันได้ (คนละห้อง หรือคนละหัวทางเดิน) พกแท็กสวมใส่ (C10 / B7 / B10) แล้วเดินข้ามไปมาช้า ๆ 4–6 รอบ

- คาดหวัง: **ประมาณหนึ่งครั้งการเปลี่ยนโซนต่อการข้ามหนึ่งครั้ง** ไม่ใช่กระพริบไปมาทุก uplink
- ถ้ากระพริบ: RSSI ของสถานที่จริงแกว่งกว่าที่ปรับไว้
- ถ้าช้าเกินจนเดินถึงปลายทางแล้วยังไม่เปลี่ยน: dwell ยาวไป

ค่าคงที่อยู่ใน [`backend/internal/alerts/zone.go`](../backend/internal/alerts/zone.go): `ZoneMarginDB = 6.0` (ต้องแรงกว่าโซนเดิม 6 dB), `ZoneDwell = 10s` (ต้องแรงกว่าติดต่อกันนานเท่านี้), `ZoneFresh = 60s` (เกินนี้ถือว่าโซนเดิมไม่ได้ยินแล้ว)
**ทั้งสามค่าปรับจาก simulator เท่านั้น ยังไม่เคยจูนกับสถานที่จริง** ให้บันทึกจำนวนครั้งที่เปลี่ยนโซนเทียบกับจำนวนครั้งที่เดินข้ามจริงไว้ในตารางยอมรับ แล้วค่อยเสนอแก้ค่าพร้อมข้อมูล อย่าแก้ตามความรู้สึก (ไฟล์นี้เป็นของทีม alerts — เสนอแยก PR)

## 7. แบตเตอรี่และ advertising interval

เอกสารที่เก็บไว้ในรีโพตอนนี้ ([`docs/minew-mhs.md`](minew-mhs.md) → MG3 datasheet, หน้า MHS kit, Gateway configuration API) **ระบุเฉพาะฝั่ง gateway** ไม่มีตัวเลขอายุแบตเตอรี่หรือ advertising interval ของ S1/C10/B7/B10/E8S/MBT01

ดังนั้น:

- **อย่าเขียนตัวเลขลงเอกสารนี้จากความจำ** ให้กรอกหลังอ่านจากฉลาก/แอปตั้งค่าของแท็กจริง หรือหลังเพิ่ม datasheet ของรุ่นนั้นเข้ารีโพแล้วอ้างอิงไฟล์
